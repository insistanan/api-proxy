# 架构与代码质量优化方案

日期：2026-09-14。状态：设计稿，尚未实施。

本方案依据当前工作区的静态审查，目标是在现有模块化单体上提高正确性、可维护性和可测试性。本轮只新增本文件，未修改业务代码，未执行程序、测试、编译、基准或发布。下文中的接口名和新增路径属于拟议设计，不能当作已经存在的能力调用。

总体判断：现有模块化单体和单二进制部署适合本项目，协议转换与调度已有复用基础。按《架构整洁之道》衡量，目录划分已有基础，但核心仍与 HTTP 框架、配置和存储实现耦合。优化重点应放在正确性、依赖方向和状态归属，先处理已识别风险，再逐步改善结构。

## 1. 目标与实施边界

优先处理鉴权、熔断收尾和配置一致性，再调整依赖方向、前端职责与质量门禁。以减少一次业务修改涉及的职责和状态为目标，不把目录数、接口数、文件行数作为优化成绩。

建议遵循以下决策：

1. 保留 Go 后端、Vue 管理界面与单二进制部署；保留当前 Go module，不引入依赖注入框架、消息总线或额外服务。
2. 正确性修复与结构重构分开验收。每个切片先明确需要保持的行为，再通过单一实现完成迁移；临时适配器只转发，不复制业务。
3. 消费方确有替换或隔离需求时才定义小接口。纯函数、值对象和同包局部提取优先于新增 package。
4. 接口错误、持久化错误和非法状态显式传播，保留 `errors.Is/As` 链。未知结果不得自动解释为成功，失败写入不得被描述为未发生的操作。
5. 性能调整需要测量依据。本轮不承诺吞吐、延迟或内存提升比例，也不预设对象池、缓存或并发模型重写。

必须保持的行为边界如下；修复已确认缺陷所需的变化在对应阶段单独说明。

| 边界 | 保留要求 |
|---|---|
| 对外协议 | 五协议请求、响应、SSE 事件顺序、终止标记及既有兼容逻辑保持；已提交客户端响应后不能重新故障转移 |
| 渠道调度 | 对话路由覆盖 → 命中渠道池内的配置顺序 → 兜底分组；不恢复促销、亲和或评分改写生产顺序 |
| 模型与重试 | 模型名原样匹配、目标模型按配置顺序尝试；保留 Fuzzy 模式现有的错误分类和模型重试开关 |
| 视觉与内容安全 | 保留解析后、会话观测前的脱敏，以及上游载荷在视觉处理前后的检查；images 保留 multipart 特例 |
| 会话和用量 | 保留 Responses 历史边界、`previous_response_id` 规则，以及各协议缓存和推理 token 的计量口径 |
| 配置兼容 | 保留配置路径、JSON 字段、旧格式迁移和渠道稳定 ID；HTTP 渠道下标 API 不在本方案中整体改为 UUID API |
| 日志与数据 | 保留脱敏、留存周期、各 SQLite 库和开关含义；评测不污染生产调度指标 |
| 工具链 | 以当前 `backend-go/go.mod` 的 Go 1.25 要求为基准对齐构建入口，不在结构重构中升级业务依赖 |

现行行为参考 [invariants.md](invariants.md)、[flows.md](flows.md) 和 [capabilities.md](capabilities.md)。部分旧术语说明仍描述亲和或促销优先，实施时以已确认的配置顺序契约为准，不通过重构恢复旧策略。本方案不代替现行运行文档；完成对应切片后再同步其中的事实。

## 3. 目标依赖与目录策略

目标是让 HTTP 适配、请求编排、选渠策略和存储执行各自承担明确职责。保留现有目录作为迁移起点，先调整契约再移动文件。

| 职责 | 目标归属 | 依赖约束 |
|---|---|---|
| 装配与进程生命周期 | `main.go`，必要时在 main 包内分文件 | 创建具体实现并注入；统一安排启动、失败清理和关闭 |
| HTTP 入口与响应写回 | `internal/handlers/*`、`internal/middleware` | 负责 Gin、鉴权、HTTP 解析和 SSE 写回，调用请求编排契约 |
| 共享请求编排 | 逐步从 `handlers/proxycore` 提取到拟议的 `internal/proxy` | 不导入 Gin、`internal/handlers` 或 SQLite 实现；通过消费方小接口访问选渠、检查和观测能力 |
| 上游协议适配 | `internal/providers`、`internal/converters` | 接收显式请求输入和 `context.Context`；输出请求、转换结果及必要元数据 |
| 渠道决策与健康状态 | `internal/scheduler`、`internal/circuit` | 保留配置顺序和健康过滤；不继续作为所有存储实例的获取入口 |
| 配置和各类持久化 | `config`、`metrics`、`session`、`conversation` 等既有包 | 按本模块语义管理存储，通过窄接口向编排层提供能力 |
| 网络与文件基础能力 | `internal/httpclient`；按 R3 抽取最小的 `internal/atomicfile` | 复用现有实现，不引入业务协议分派，不成为新的杂物包 |

第一阶段仍可通过只读快照传递 `config.UpstreamConfig` 等既有值类型。这里只限制核心直接操作 ConfigManager、文件和数据库；不宣称迁移初期整个传递依赖闭包已经纯化。确实需要移动类型时，再按消费关系确定归属，不提前创建笼统的 domain/common/types 新包。

`core/channelcrud` 是共享 HTTP handler，最终应归入 `handlers/channelcrud`。该移动放在行为固定之后，独立于 CRUD 语义修改。五协议仍复用同一份 CRUD 和路由注册逻辑。

## 4. R1：收紧管理鉴权边界

### 4.1 设计决策

1. 为 `/api` 和 `/admin` 路由组显式绑定管理鉴权。密钥提取与比较复用现有规则；管理日志与代理错误响应仍保留各自格式。
2. `WebAuthMiddleware` 只承担页面和 Web UI 开关策略，不能因 URL 后缀放行管理业务。静态资源按已注册的资源路径处理，不能对任意请求套用扩展名白名单。
3. 五协议代理继续走现有统一鉴权入口，避免在路由组和 `RunProxyRequest` 内重复鉴权。`/health`、登录页面和必要静态资源保持可访问。
4. 保留 CORS 中间件处理预检的顺序。`OPTIONS` 的预检放行不能转而执行业务 handler；Web UI 关闭时保留管理端点不可用的行为。
5. provider ID 的合法字符集不承担鉴权职责。已有合法 ID 可以继续使用，修复点放在路由鉴权，而非禁止 `.js` 字符串掩盖问题。

涉及文件：`backend-go/main.go`、`internal/middleware/auth.go`、`auth_test.go`；必要时在 main 包内提取可用测试依赖装配的路由函数，不启动完整应用。

### 4.2 验收场景

| 场景 | 必须满足的结果 |
|---|---|
| 已注册管理路由，无密钥或错误密钥 | 返回现有未授权错误，业务 handler 和存储写入均未执行 |
| 动态 ID 为 `demo.js`、`demo.css` 等合法值 | GET、PUT、PATCH、DELETE 等实际已注册方法都不能绕过鉴权 |
| 带后缀的 provider 已存在 | 在临时目录中构造记录，验证其详情和修改端点仍要求密钥；不接触用户真实配置 |
| 正确密钥 | 合法管理操作保持原有结果；不存在的 ID 由业务层正常返回错误 |
| 页面、资源、健康检查、CORS 预检 | 既有访问流程保持，预检不触发业务副作用 |
| 五协议代理、Web UI 关闭模式 | 代理鉴权保持，管理接口禁用行为保持 |

该切片不同时引入用户系统、会话登录或权限角色。若以后加强默认访问密钥的启动校验，应单独声明部署行为变化。

## 5. R2：统一结果语义与熔断许可生命周期

### 5.1 分开表达三件事

在 `proxycore` 内先就地改造尝试结果，不先搬包：

- 请求接下来如何处理：完成、尝试下一个 Key、下一个模型或下一个渠道。各层只消费属于自己的重试决定。
- 客户端响应是否已经提交：一旦提交，不允许重试并写出第二份响应。
- 当前渠道的健康结果：成功、真实渠道故障、中性结束。它不能由 `SuccessKey` 是否为空或 `LastError != nil` 推断。

上游状态码、错误体与 `errors.Is/As` 可识别错误保留为诊断信息；跨 Key、模型和渠道传递时不能用新的普通字符串错误覆盖分类。保留 Key 级指标与渠道级熔断两种粒度，不能用一次 Key 失败直接替代整个渠道的最终结果。

| 本渠道结束原因 | 渠道健康结果 | 重试决定 |
|---|---|---|
| 最终成功，包括前面有候选失败 | 成功 | 完成 |
| 可重试的真实故障耗尽渠道内候选 | 失败 | 按既有顺序尝试下一渠道 |
| 不可重试的请求参数、尺寸等错误 | 中性 | 返回该协议错误，不继续轮询 |
| 内容审核拒绝或本地内容安全阻断 | 中性 | 仅按当前协议允许的审核转移规则选择下一渠道，否则完成 |
| 客户端明确取消 | 中性 | 立即停止 |
| 响应已提交后的真实上游中断 | 失败 | 终止当前流，不再故障转移 |
| 本地配置、构建或检查系统错误 | 中性 | 显式返回内部错误，不把本地问题计为上游故障 |

“最终结果”指导致本渠道结束的明确决定。之前的 Key 失败继续留在 Key 级记录；最终取消或审核拒绝不能因为曾出现一次失败而重新算成渠道故障。未知结果是程序错误，必须可见，不补成默认成功。

### 5.2 许可所有权

渠道选中时取得一个请求范围内的许可句柄，持有在途预留和本次真正取得的半开探测名额。该句柄放在现有 scheduler/circuit 边界，不创建通用资源管理框架。

1. `Peek` 只预检。正式 `Allow` 拒绝时，立即归还本次在途预留，返回明确的候选不可用结果，由选渠逻辑有界地继续选择；不能清掉 `Probe` 标志后继续发送。
2. 单渠道、多渠道、固定渠道、视觉旁路及 `llmgate` 使用同一许可收尾规则。对话覆盖不等于跳过熔断；管理端快捷测试保留显式例外。
3. 正常结束必须提交明确的健康结果，并恰好记录一次。许可释放允许幂等，但重复结果记账视为契约错误，测试必须能够发现。
4. 取得许可后立即安排 `defer` 释放。异常退出的保底动作只释放自己拥有的资源，并明确记录未正常终结的状态；不能吞掉 panic，也不能伪造成功指标。
5. 许可绑定取得时的 breaker 实例或状态代次。手动重置后的旧请求不能归还新探测的名额；渠道重排后的旧请求不能按新下标误记另一渠道。
6. 快捷测试绕过普通准入时，不占用或释放其他请求的半开名额。其健康结果如何影响恢复沿用已确认规则，并与许可释放分开实现。
7. 保留 Key、URL、请求日志和会话记录的既有统计职责；R2 只统一完成信号，不顺带改费用或 usage 算法。

涉及文件：`internal/circuit/circuit.go`、`internal/scheduler/selection.go`，以及 `proxycore` 的 `protocol.go`、`multi_channel_failover.go`、`upstream_attempt*.go`、`upstream_failover.go`。检查 `visionlayer` 和 `llmgate` 的选渠出口，禁止只修公开代理入口。

### 5.3 验收场景

- 半开探测分别遇到成功、不可重试 413、审核拒绝、取消、构建失败和已提交流中断，最终都没有遗留探测名额。
- 内容审核转移不增加渠道失败计数；真实渠道失败仍能触发 Open。
- 两个请求同时通过预检后，正式准入最多放行一个半开探测；被拒绝者不发送上游请求。
- 取得许可后发生路由冲突、空 Key 等提前返回，以及 panic 清理路径，均不遗留在途预留。
- 手动重置、渠道重排和迟到完成交错时，结果只作用于原有请求身份，不释放新许可。
- 流已提交后错误不发送第二次上游请求；正常完成、取消和失败的日志、会话结束记录各执行一次。

并发用例通过可控屏障和可控时间推进触发，不靠长时间 sleep 碰撞概率。此处修改完成后再推进 R4 的编排迁移。

## 6. R3：配置事务、原子写入和热重载一起收敛

### 6.1 唯一变更入口

所有配置修改统一经过以下顺序：

`读取当前快照 → 深拷贝候选 → 应用变更 → 校验完整候选 → 序列化 → 备份旧文件 → 写入并替换 → 发布新快照 → 执行提交后通知`

第一版沿用当前互斥锁串行提交，不同时改成无锁读写或异步持久化。锁覆盖需要保持一致的提交过程；跨模块通知在合适的锁边界外执行，避免回调再次取配置锁造成死锁。

- 只克隆配置数据，不能复制含锁的 `ConfigManager`。复用 `UpstreamConfig.Clone`，补齐 Settings 中嵌套 slice、map、指针等的复制；保留 nil 与空集合的序列化差异。
- 校验器接收候选配置，不在 `cm.config` 上边改边检查。读者只能拿到完整旧快照或完整新快照，不能取得可修改的内部集合。
- 新增、修改、删除、复制、重排、Key 管理、状态、促销、渠道池、设置、兼容能力标记及生命周期维护都迁入同一提交入口。
- 清理失败 Key、重置关联状态等副作用放在提交之后。提交前失败不能留下配置以外的“已经删除”状态。
- 内存中的临时健康计数与持久化配置分别管理；每次请求不为无变化的配置重复落盘。

### 6.2 复用原子写入底座

已有 [piagent/fileio.go](../backend-go/internal/piagent/fileio.go) 和 [pricing/store.go](../backend-go/internal/pricing/store.go) 提供临时文件写入经验。抽取其中与业务无关的最小原语到 `internal/atomicfile`，不让 `config` 反向依赖 `piagent`，也不复制出第三套平台替换代码。

该原语只负责同目录临时文件、权限、完整写入、同步、关闭和平台替换。pi-agent 的 revision、跨进程锁、备份约定继续留在 piagent；配置备份数量及命名策略留在 config。先服务 config 和原实现的委托入口，其他存量写入器在单独核对契约后再迁移。

明确以下提交语义：

| 失败位置 | 内存与磁盘行为 | 向调用方表达 |
|---|---|---|
| 候选校验、编码、备份、临时文件创建/写入/同步/关闭、替换前失败 | 当前快照和原配置文件保持；清理本次临时文件 | 明确失败，未提交 |
| 替换成功 | 以文件替换作为提交点，发布对应的新快照 | 成功结果可见 |
| 替换成功后的目录同步或提交后通知失败 | 保持内存与已经替换的新文件一致，不能回滚内存伪装未提交 | 返回可识别的已提交错误；界面读取实际状态，不自动重做修改 |

建议以内部错误类型携带失败阶段、底层错误和 `Committed` 状态，使用 `%w` 保留错误链。需要返回给前端时，在现有错误响应上增加可选的 `code` 和 `committed` 信息；这是本方案明确提出的兼容性扩展，不改变成功响应结构。配置管理 API、助手配置动作等调用方都必须识别已提交结果，防止一次新增被重试成两次。

Windows 复用现有替换方式，Unix 使用同目录 rename，并显式处理平台支持的目录同步。不能把任意同步错误吞掉，也不能承诺所有平台在断电时具有同样的持久性。配置与备份包含密钥，沿用受限权限策略；新文件在 Unix 上使用 0600，Windows 按目标目录 ACL 管理，不在重构中放宽现有访问权限。

### 6.3 热重载必须同步调整

当前监听目标文件的 Write 事件，原子替换可能改变文件对象，单改保存函数会使监听失效。因此 R3 的可交付边界必须同时包含保存和监听。

1. 监听配置所在目录，按规范化后的目标路径过滤；覆盖目标文件的 Write、Create、Rename/Remove 等相关变化，忽略临时文件和备份文件。Windows 路径比较遵循平台规则。
2. 合并短时间事件后重新读取目标；不要假设一次事件等于一次完整写入。合并等待必须有上限，不无限延后重载。
3. 解码、补默认值、迁移、归一化与校验全部在临时候选中进行。失败保留最后一次有效快照，记录明确错误；不能继续解码到 `cm.config`。
4. 运行期间目标文件短暂缺失或内容不完整时，保留有效快照并报告问题；不能触发启动时的“创建默认配置”逻辑覆盖用户数据。后续有效文件出现时恢复重载。
5. 对自身提交使用内容摘要或内部版本去重，避免保存、重载、再保存形成循环；摘要只用于版本比较，不输出配置原文。
6. 配置写入与重载由同一串行入口协调。初始化监听失败要显式返回错误；关闭时等待 watcher 和生命周期工作退出，之后再关闭下游资源。
7. 当前请求保留已经取得的渠道与脱敏快照，新请求读取新配置。命令闸门的实时用户决定仍能影响正在等待的请求，不能被“大快照”冻结。

本阶段保证进程内提交、读取和重载的一致性，不把进程内互斥锁当成跨进程锁。任意外部编辑器与 API 同时覆盖同一文件的冲突需要单独约定；检测到目标版本已变化时明确拒绝本次提交并重读，仍不能宣称这消除了所有外部写入竞争。多实例共享配置文件不作为本方案的完成条件。

### 6.4 验收场景与文件范围

| 场景 | 必须满足的结果 |
|---|---|
| 删除、重排、增删 Key 保存失败 | 内存配置、磁盘旧文件及提交前关联状态不变 |
| 候选含非法设置或深层集合被修改 | 非法候选不发布，旧快照没有别名写入污染 |
| 临时文件写入及替换各阶段故障注入 | 原文件不会被截断，未提交与已提交结果可区分 |
| 连续原子替换、编辑器保存、短暂删建 | watcher 持续工作，最终加载有效版本 |
| 无效 JSON、合法 JSON 但业务校验失败 | 保留有效配置，记录错误，不自动生成默认文件 |
| 自身提交与 watcher 重载交错 | 不重复提交、无循环保存，新请求看到完整版本 |
| 提交后失败、关闭期间重载 | 调用方不盲目重试；后台工作结束后才释放资源 |

涉及文件：`internal/config/config.go`、`config_loader.go`、`channel_set.go`、`config_lifecycle.go`、各配置修改入口和新事务测试；最小 `internal/atomicfile` 平台实现及复用入口；管理 API 的已提交错误映射。该阶段保持现有 JSON 格式及迁移规则，不改变数据库 schema。

## 7. R4：后端边界解耦

### 7.1 先解除实际耦合，再移动编排

按下列顺序实施，每一步保持现有调用入口可用：

1. **收敛错误分类。** 将容量错误等共享谓词统一放到已有的 `internal/utils/upstream_error.go`，复用既有分类口径。各 provider 与重试决策调用同一实现；通过错误样本固定分类边界，避免不同层把同一错误解释成不同结果。
2. **让 Provider 接收显式输入。** 以 `context.Context` 传递取消和截止时间，使用有类型的请求值传递模型、协议、渠道快照等输入，返回构造后的上游请求及必要转换元数据。先清点 Gin `Get/Set`：请求输入由入口解析，转换产物由返回值表达，会话决定由编排持有。不能把所有状态改塞进 `map[string]any`，也不能滥用 context value 隐藏业务参数。旧 Gin 方法暂时保留为薄委托，先迁移 llmgate、vision 的请求构造，再逐个迁移公开协议。
3. **复用唯一网络发送实现。** 将 `proxycore.SendRequest` 中的网络部分收敛到已有 `internal/httpclient`，传入已解析的超时、代理、TLS 等发送选项；调用层负责业务日志和结果分类。明确请求体重放条件、响应体关闭责任、取消传播与流式读取边界，避免新增第二套 sender。`eval.Sender` 随之解除对 handlers/proxycore 的依赖。
4. **提取纯请求编排。** R2、R3 的行为稳定后，将与 Gin 无关的尝试顺序、重试决策、许可收尾和观测调用逐步移到拟议的 `internal/proxy`。HTTP 鉴权、协议解析和响应写回留在 handlers；核心通过消费方定义的最小输出契约获知响应是否已提交。SSE 写入失败和取消必须能返回核心，不能因隔离 HTTP 而丢失收尾信息。
5. **缩小 scheduler 的职责。** scheduler 保留选渠、健康和许可所需依赖；请求日志、会话观测等由编排直接接受相应的小接口。逐项迁移 `GetConversationRegistry`、`GetRequestLogStore`、`GetProfileManager` 的外部使用，使 scheduler 退出服务定位器角色。仍参与策略或观测的数据按实际用途保留，不能连带删除。
6. **整理装配与生命周期。** main 保持具体实现的装配入口，可在 main 包内按初始化职责分文件。初始化中途失败时按逆序清理已创建资源；停机先停止新请求和后台生产者，再等待或有界取消在途工作，最后关闭数据库与文件。保留现有部署形态，不另建生命周期框架。

容量分类修复可以先于编排迁移单独交付。`core/channelcrud` 的目录移动放在调用关系稳定后作为独立机械变更，避免与 CRUD 行为修复混审。

### 7.2 内部调用的保留边界

| 调用方 | 可以复用 | 必须保持的区别 |
|---|---|---|
| 五协议公开入口 | Provider 构造、网络发送、生产编排 | 保留统一鉴权、配置顺序调度、协议输出和生产观测 |
| llmgate / vision | Provider 构造、网络发送、所需的许可与健康契约 | 不直接套用公开 `RunProxyRequest`；避免闸门审核自身、视觉再次分流及重复记账 |
| eval | 网络发送与原有底层连接配置 | 保留原生发送、不做协议转换、不进入生产调度的行为；不继承管理请求的 cookie 或访问密钥 |

`llmgate` 完成迁移后，应能直接用显式输入构造请求，不再调用 `gin.CreateTestContextOnly(noopResponseWriter{}, gin.New())`。内部调用是否计入某类指标以现有契约为准，不借统一入口改变业务语义。

### 7.3 验收与涉及范围

- 用内存中的选渠、发送和观测替身验证编排，覆盖模型顺序、Key 切换、渠道切换、取消、SSE 提交后错误以及一次收尾；这组测试无需 Gin、真实配置文件或 SQLite。
- Provider 转换前后以同一组固定样本比对请求方法、目标、头、载荷和元数据；脱敏后比对，不向真实上游双发请求。
- 以导入规则约束拟议 `internal/proxy` 不直接依赖 Gin、handlers 或 SQLite 驱动；不要求在第一步清空现有值类型的所有间接依赖。
- 检查每个响应体与后台任务都有明确关闭方，启动失败和正常退出都可完成清理。

涉及 `internal/providers`、`converters`、`httpclient`、`handlers/proxycore`、`llmgate`、`visionlayer`、`eval`、`scheduler` 及 main 装配；按上述顺序分批修改，不作为一次跨全仓重写。评价结果看核心能否独立验证、一次需求变更是否减少跨职责修改，不设拆包数量指标。

## 8. R5：前端职责与状态归属

### 8.1 按业务职责拆分

| 现有位置 | 调整后的职责 | 迁移方式 |
|---|---|---|
| `App.vue` | 页面壳、导航和全局组件 | 认证流程提取到独立 composable；渠道业务逐步归入拟议 `ChannelsView` 和现有 store |
| `ChannelOrchestration.vue` | 组织渠道页面的交互 | 在 `components/channels/` 按渠道展示、指标、日志/评测、操作弹窗拆分；父组件只协调所需状态和事件 |
| `AddChannelModal.vue` | 弹窗入口与提交交互 | 将编辑、校验和 payload 组装收敛到拟议 `useChannelEditor`；按连接、Key、模型映射、视觉配置等实际职责拆表单 |
| `api.ts` | 保留过渡导出入口 | 按渠道、设置、日志、评测等业务拆模块；保留 `channelApiByType` 等既有导出，待调用方迁移后收敛 |

继续复用 `quickInputParser.ts`、`channelDefaults.ts`、`useChannelModelImport.ts`、`useAutoRefresh.ts` 和已有 Pinia stores。拆文件时以复用和状态归属为依据，避免每个小组件重新实现解析、默认值、轮询和错误提示。此次保持现有框架与交互，不包含视觉改版，也不设置任意文件行数硬阈值。

### 8.2 明确数据的唯一来源

- **服务端数据**：渠道列表、dashboard 及共享刷新状态由对应 store 管理，同一查询不在页面和子组件各维护一份轮询。查询键包含协议种类和必要筛选条件，组件只消费它需要的切片。
- **编辑状态**：表单持有独立草稿；取消不修改 store，保存成功后以服务端结果刷新。保存失败显示具体错误，不能先弹成功再依靠下一轮刷新修正。R3 的已提交错误要提示实际结果待刷新，禁止自动重复新增或删除。
- **局部界面状态**：展开项、弹窗开关、当前焦点留在最近的共同使用组件；没有跨组件需求的状态不搬进全局 store。
- **认证状态**：使用统一来源。请求层通过注入的凭据 getter 获取当前认证信息，避免通用 transport 直接依赖 Pinia；登出时使旧请求结果失效，并清理受保护数据。

异步请求发起时捕获协议种类、稳定渠道 ID 和本次请求代次。返回时核对目标和代次，过期结果不得写入当前 tab；卸载、切换和登出通过取消或代次校验阻止回填。轮询不能重入，手动刷新与定时刷新复用同一调度入口；失败可保留旧数据，但必须呈现刷新错误和旧数据状态。

本地缓存和编辑目标用稳定 ID 关联，避免重排后下标指向另一渠道。保持当前下标 API 时，应从最新列表解析提交下标，无法确认目标时显式停止并要求刷新。该措施只改善客户端自身状态；其他客户端恰好同时重排的竞争，需要后续以版本校验或 ID API 单独治理，不能声称本次前端拆分已消除它。

请求底座统一类型化响应与 `ApiError`，保留 HTTP 状态、业务错误码及可选 `committed` 信息；业务模块负责解释结果。不能把失败转成空数组、默认对象或成功状态，也不能在异常文本中暴露密钥。

### 8.3 验收与涉及范围

优先为以下实际风险补前端测试：切 tab 或登出后请求晚到；轮询与手动刷新并发；保存失败；已提交错误后刷新；拖拽重排后的编辑目标；密钥掩码被误当作真实密钥回传。编辑流程保持已有“保留、替换、删除 Key”的语义，并通过 payload 样本覆盖模型映射和视觉字段。

以相同操作得到相同请求与页面结果为迁移标准；子组件不额外发起重复请求，认证和错误展示保持一致。涉及上述 Vue 组件、渠道视图、composables、stores 和 API 模块，按“状态归属 → 异步生命周期 → 展示拆分”分批推进，避免先拆模板再复制状态。

## 9. R6：旧策略与质量门禁收敛

### 9.1 让实现与维护说明一致

当前生产选渠遵循配置顺序。先核对全仓引用及实际入口，再退役不再参与生产路径的 adaptive/promotion 选渠函数，修正误导的“已启用自适应负载均衡”启动日志。仍被观测、管理 API 或界面消费的 `ProfileManager`、metrics、亲和/促销字段继续保留；字段名字不能作为删除依据。

旧调用方先委托到已确认的行为，确认没有有效消费者后再删除旧入口。历史持久化字段和 API 兼容另行评估，不与死代码清理捆绑。实现完成后同步 `docs/flows.md`、`invariants.md`、`capabilities.md`、`glossary.md` 以及后端 `CLAUDE.md` 中的过时说明；方案阶段不提前修改这些事实文档。

### 9.2 收敛验证与工具链

1. 保持根目录 `npm run check` 为完整检查入口。在已有检查上逐步接入前端 Vitest、ESLint 和新核心的依赖约束，让新增逻辑进入统一验证范围。
2. ESLint 存量问题以独立、可审查的切片整理；不全仓执行自动修复，不通过关闭规则掩盖实际错误。新增检查在对应存量处理后启用，不能长期保留只输出警告的假门禁。
3. 增加 PR 验证 workflow，发布流程复用同一检查入口。现有 pre-commit 可以保留轻量行尾检查，但不能作为全量验证通过的依据。
4. 以 `backend-go/go.mod` 的 Go 1.25 为依据统一开发说明、CI 和 Docker；CI 优先读取 `go-version-file`，镜像版本同步维护。只修复工具链不一致，不附带业务依赖升级。
5. 前端当前同时跟踪 `frontend/bun.lock` 与 `frontend/package-lock.json`。包管理器收敛单独处理：建议对齐根检查入口使用 npm 与 package-lock；实施前对比锁定依赖和现有构建步骤，明确唯一权威锁文件，再更新对应入口。不能直接删除一个锁文件后重新解析全量依赖，把升级混进架构重构。
6. 并发相关的 race 检查放在具备所需 C 工具链的 Linux CI；配置替换与 watcher 的平台行为同时在 Windows 验证。不用一个平台通过推断另一个平台的文件语义。

门禁结果应能指出真实失败原因，命令不存在或工具链缺失应显式报告。依赖约束优先利用现有 Go 工具和仓库脚本，只覆盖明确禁止的关系，不为此引入通用架构框架。

| R5 前端状态与组件 | API 兼容约定固定 | 先收敛状态和异步流程，再拆页面与表单 | 晚到结果、重复刷新和错误保存用例通过，交互保持 |
| R6 门禁与旧策略 | 按子项分别满足 | 工具链 / CI 可早接；旧策略在引用迁移后退役 | 同一门禁覆盖本地与 PR，文档和实际策略一致 |

R5 可以独立推进；R3 的 `committed` 错误消费需要前后端配套。R4 的输入和传输整理可以先准备，但生产编排切换必须等待 R2、R3 稳定。单个切片如无法在一次审查中清楚说明行为变化，应按契约或调用入口继续拆分。

测试优先覆盖可观察的行为和故障边界，不为了拆文件补与实现逐行对应的测试。配置测试用临时目录、可控写入故障和事件等待；避免依赖固定长 sleep。HTTP 测试用 `httptest` 与本地替身，不使用真实密钥或真实上游。Windows 的替换与重载场景需要实际在该平台验证。

## 11. 回退与完成标准

### 11.1 回退安排

- 每个结构调整独立交付，保持原配置格式、数据库 schema 和公共协议，便于撤回单个切片。临时适配器只做委托，迁移结束后退役，避免长期维护两套业务实现。
- 先用固定样本和本地替身比较新旧行为；不向真实上游双发请求，也不重复执行配置动作或助手副作用来对比结果。
- 回退后续结构调整时保留 R1 的鉴权修复。正确性修复与结构变更分开，使撤回结构代码不连带恢复已确认缺陷。
- 配置相关代码回退前核对新文件与旧程序的兼容性，以及 watcher 与原子写实现是否成套。备份仅供明确恢复操作使用，不能在提交后出错时自动拿备份覆盖现有配置。
- 若发现回归，停止该切片后续迁移，记录复现条件与受影响契约，再修复或撤回。不能通过吞掉错误、重复调用或隐藏告警维持表面成功。

### 11.2 完成标准

以下条件全部有实现及验证证据后，才可将对应阶段标记为完成：

1. 管理路由的鉴权不受后缀或 provider ID 影响，代理与 Web UI 既有边界保持。
2. 每次已准入尝试有唯一许可和确定收尾；未准入不发送；中性结果不被记为渠道失败，响应已提交后不重试。
3. 配置提交前失败不改变有效状态，提交后异常能表达实际结果；无效重载保留最后有效配置，连续原子替换不破坏监听。
4. 核心请求编排可脱离 Gin、真实文件和数据库验证；内部调用无需伪造 HTTP 框架上下文，资源生命周期有明确所有者。
5. 前端共享数据和认证各有唯一来源，异步结果不会写入错误的协议或渠道；保存错误和刷新错误可见。
6. 生产选渠策略、启动日志和维护文档一致；兼容字段的有效消费者得到保留。
7. 工具链一致，相关行为测试、并发/平台验证和统一门禁有实际记录；未执行的检查保持“未验证”状态。

本方案对《架构整洁之道》的采用重点是依赖方向、职责边界和业务规则的可独立验证性；对 KISS / YAGNI 的落实是保留模块化单体、按真实变化提取小接口，并让过渡层及时退出。没有测量基线时不把性能收益作为完成标准；如后续出现已测得的瓶颈，再单独制定优化切片。
