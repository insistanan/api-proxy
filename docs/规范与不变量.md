# 规范与关键不变量（Conventions & Invariants）

本文档记录了 **api-proxy** 在架构演进中沉淀的核心设计不变量、工程规范以及常见踩坑防范。在编写或修改代码前，请务必仔细阅读，确保改动与整体设计保持一致。

---

## 1. 通用开发原则

- **清晰显式的错误处理**：不静默兜底，不吞掉异常，坚决不用无意义的默认值掩盖底层故障。出现错误时，必须返回或包装（`fmt.Errorf("%w")`）具有明确业务语义的中文字符串。
- **克制与务实**：改动紧扣实际需求，遵循 KISS、YAGNI 原则。不为了“形式上的完整”而编写过度复杂的泛型、抽象层或暂时用不到的代码。
- **本地门禁第一**：代码提交前必须在本地确保 `npm run check`（或 `make check`）全部通过。全量门禁包含行尾检查、gofmt、go vet、go test、前端类型校验、图标注册扫描、单元测试以及 ESLint `--max-warnings 0`。
- **统一的日志格式**：后端统一使用标准 `log.Printf`，格式遵循 `[组件-动作] 中文说明`，例如 `[Circuit-Init] 熔断器初始化成功`、`[Auth-Failed] 无效的访问凭证`。

## 2. 后端关键不变量（Backend Invariants）

在修改后端调度、代理处理和数据存储逻辑时，必须严格遵守以下关键约束：

### 2.1 优雅停机的严格逆序原则
服务的关闭流程必须按依赖关系的**绝对逆序**执行：
1. **停止接收请求并排空在途流量**：先停止 Web 引擎接收新请求，并等待进行中的 HTTP 请求完成或超时；
2. **停止后台任务与数据生产者**：停止调度器心跳、配置热重载监听器和指标采集器，等待所有常驻后台 goroutine 退出；
3. **关闭存储连接池**：在所有可能产生数据写入的组件完全停下后，将日志队列积压数据完整刷盘，最后关闭各个 SQLite 连接。
> **原因**：如果先关闭数据库连接，正在处理中的代理请求会因写入日志或读取映射而产生大量数据库报错；启动失败时的清理逻辑与优雅停机共用同一套清理闭包注册表。

### 2.2 生产选渠顺序与促销约束
- **基础顺序**：多渠道请求默认严格遵循配置文件中的物理排列顺序。
- **促销渠道约束**：
  - 开启“促销”标记且处于健康状态的渠道，仅在**同分组**内部临时拥有优先调度权；
  - 促销不能跨越渠道组（例如 Chat 组的促销渠道绝不能被 Messages 组选中）；
  - 对话绑定的会话路由（Session Affinity）优先级高于促销；
  - 促销渠道一旦达到预设的时长或成功请求次数上限，立即平滑退回原本的配置顺序；
  - 若所有渠道均不健康，系统在进行探测恢复时，依然严格按配置先后顺序尝试。
- **性能画像仅作观测**：ProfileManager 统计的首字延迟和传输速率仅供展示，**严禁参与选渠排序**，以防网络抖动诱发流量震荡。

### 2.3 准入控制必须按“实际凭据”聚合，而非渠道名
在并发控制（`upstreamcontrol`）中，必须以 `[目标 URL + 实际物理上游协议 + API Key]` 三元组作为并发计数和排队的键名。
> **原因**：管理员可能在配置中创建多个别名渠道，但它们底层指向完全相同的物理服务节点与 API Key。如果按渠道名做限流，多个渠道并发相加会直接导致上游返回 429 封禁。只有按实际物理凭据做共享准入，才能真正保护上游配额。

### 2.4 流式响应的 Context 传播与资源及时关闭
- Provider 的流式转换统一使用 `HandleStreamResponseCtx`。
- 原生转发与转换流必须将 Gin 请求的 `Context` 透传给底层的 HTTP 发送逻辑；
- 在任何流式转发退出时（无论正常结束、出错还是客户端主动断开连接），**必须立即关闭上游响应的 Body**。
> **原因**：如果客户端关闭了浏览器标签页而后端没有断开上游连接，上游的大模型推理会继续进行并持续产生计费，同时后端的读取 goroutine 会永久阻塞造成内存泄漏。

### 2.5 ChannelPermit（选渠许可）生命周期
从调度器获得 `ChannelPermit` 之后，必须立即通过 `defer permit.Release()` 登记释放。请求结束时，按执行结果调用一次 `permit.RecordHealth(...)`。
- `RecordHealth` 与 `Release` 内部均设计为幂等操作，但每一次选渠尝试在语义上只能计入一次健康结果。

### 2.6 Messages 转换 Responses 时的 Provider 实例复用
当客户端以 Claude Messages 协议请求、而目标上游为 OpenAI Responses 时，请求组装（Build）与成功响应处理（HandleSuccess）**必须复用同一个 Provider 实例**（保存在 Gin 的上下文中）。
> **原因**：OpenAI Responses 协议依赖上下文维系前序对话链（`previous_response_id`），若每次处理响应时重新构造 Provider 实例，会导致会话链断裂，后续轮次对话将失去上下文记忆。

### 2.7 重启后遗留审批记录的自动失效
危险命令 AI 闸门在拦截到高风险命令后，会在数据库中保存一条状态为 `waiting` 的待审批记录，内存中通过 channel 挂起等待管理员确认。
- 一旦程序重启，内存中的等待 channel 已经销毁，任何遗留的 `waiting` 状态记录必须在启动阶段由 `GateStore.ExpireStalePending` 自动标记为失效拦截，严禁在重启后错误地放行高风险命令。

### 2.8 配置热重载的完整原子快照
配置管理器在加载或修改 `config.json` 时，采用“原子写”（写入临时文件后重命名覆盖）和“全量候选替换”机制。
- 读取方在任何时刻只能获取到一份完整可用的旧配置快照，或者一份完整校验通过的新配置快照，绝不允许出现半更新或脏读状态。

## 3. 前端关键约定（Frontend Conventions）

### 3.1 状态唯一真理源与编辑草稿分离
- **共享领域状态**（如已保存的渠道列表、全局设置、当前登录凭据）由 Pinia Store 集中管理，作为全局唯一真理源。
- **页面编辑草稿**（如渠道弹窗表单、高级兼容配置）由 Composable 或组件局部维护：
  - 用户在界面修改表单时，仅变更本地草稿状态，不污染 Pinia Store；
  - 只有在点击“保存”且后端 API 返回成功后，才通知 Store 更新已保存数据；
  - 若用户点击“取消”或关闭弹窗，直接丢弃草稿，Pinia Store 中原有的数据保持不变。

### 3.2 图标按需引入与注册检查
前端采用 Vuetify 3 并关闭了全局图标自动扫描（`autoImport: false`）。
- **约定**：在模板中使用任何新的 `mdi-*` 图标前，必须先在 `src/plugins/vuetify.ts` 的 `iconMap` 中显式导入和注册 SVG 路径；
- **门禁防线**：构建和本地提交时会执行 `npm run check:icons`。如果有未注册即使用的图标，门禁会直接报错并阻止提交。

### 3.3 路由视图的“单真实 DOM 根节点”约束
在 `src/App.vue` 中，主内容区采用了路由切换过渡动画：`<transition mode="out-in">`。
- **约束**：**所有视图组件（`views/*.vue`）的最外层根节点必须是单个真实的 HTML DOM 元素**（例如 `<div>`），严禁使用 Vue 3 的多根节点（Fragment）或者把根节点包裹在 `<template>` 内部；
- **后果**：如果视图使用了多根节点，Vue 在执行淡入淡出过渡时无法正确定位动画挂载点，会导致切换路由时整个页面彻底变白。

### 3.4 错误语义中的 `committed` 标识
在渠道保存或批量更新操作中，若后端发生严重异常，可能会返回带有 `committed: true` 的错误对象：
- **含义**：表示底层配置文件或数据库实际上已经原子写入成功，但在后续的轻量收尾操作（如触发热重载广播）中失败；
- **处理方式**：前端捕获到该错误时，**严禁自动发起重试**（重试可能导致重复创建或配置覆盖冲突），而应向用户弹出明确提示，建议用户刷新页面核对最新状态。

### 3.5 鉴权与流式数据读取
- 前端管理接口统一通过 `src/services/http.ts` 发起请求，并在请求头中自动注入保存的访问密钥；
- 对于需要鉴权的数据流（如日志实时推送），**不能直接使用原生 EventSource**（因为原生 EventSource 无法在 HTTP 请求头中添加自定义鉴权头），必须通过基于原生 `fetch` 封装的 `utils/sse.ts` 中的 `readSSEStream` 函数来读取。

## 4. 文档与版本维护约定

1. **唯一功能史料**：`CHANGELOG.md` 是项目功能变更的唯一官方中文档案。每个版本在通过 `version-bump` 技能发布前，必须在 CHANGELOG 中详实记录新增特性、问题修复与系统优化。
2. **文档结构规范**：
   - 详细设计与使用说明统一存放在根目录的 `docs/` 下；
   - 根目录及子目录下的 `AGENTS.md` 仅保留最核心的职责划分与导航索引；
   - `CLAUDE.md` 文件仅包含单行 `@AGENTS.md` 引用（Windows 环境下 symlink 会被 Git 退化为普通文本文件，严禁使用软链接）；
3. **保持文档与代码同步**：当修改了渠道类型、协议参数、接口路径或鉴权逻辑时，必须同步更新相关文档，确保文档描述与代码实现的逻辑颗粒度完全对齐。
