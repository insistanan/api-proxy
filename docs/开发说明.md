# 本地开发与运维说明（Development）

本文档面向日常参与项目开发的工程师，介绍本地开发环境的准备、常用调试命令、全量门禁检查、发布流转以及 Docker 部署指南。在动手编写业务代码前，建议同时阅读 [规范与关键不变量](规范与不变量.md)。

---

## 1. 本地环境准备

开发前请确认本地已具备以下基础工具链：

- **Go 语言环境**：最低版本要求为 1.26.0，正式构建锁定工具链版本为 `1.26.10`（见 `backend-go/go.mod`）。你可以直接通过命令 `go env -w GOTOOLCHAIN=go1.26.10+auto` 让 Go 自动按需下载匹配的工具链，无须破坏系统全局的基础 Go 安装。
- **Node.js / Bun 环境**：
  - Node.js 要求版本为 `24.16.0`（见根目录 `.node-version`）；
  - Bun 要求版本为 `1.4.4`（见根目录 `.bun-version`）；
  - 前端既可以使用 `npm` 也可以使用 `bun`。仓库中同时维护了 `package-lock.json` 与 `bun.lock`，**如果在前端修改或安装了新的依赖包，请务必保持两份锁文件同步更新**。
- **构建工具**：
  - Linux / macOS 推荐使用系统自带的 `make`；
  - Windows 环境下推荐在 **Git Bash** 中执行命令。如果在 Windows PowerShell 或 CMD 中未安装 `make`，可直接在根目录下运行 `npm run check`，它会执行完全相同的门禁检查逻辑。
- **热重载工具（可选但推荐）**：
  - 后端支持使用 [Air](https://github.com/air-verse/air)（v1.67.4）实现代码保存自动重启；
  - 前端基于 Vite，自带毫秒级 HMR 模块热重载。

## 2. 常用开发命令速查

### 2.1 根目录集成命令（推荐）

| 命令 | 适用场景与具体行为 |
|---|---|
| `make dev` | **一键启动全栈开发**：同时启动前端 Vite 开发服务器与后端 Air 热重载服务。 |
| `make build` | **全栈生产编译**：构建前端代码 → 自动复制产物到后端 → 编译 Go 二进制，最终产物为 `dist/api-proxy-go`。 |
| `make run` | **快速编译并运行**：打包前端并嵌入后端，随后直接以源码方式启动 Go 服务。 |
| `make check` 或 `npm run check` | **本地全量门禁**：在提交代码前必跑，涵盖行尾规则、代码格式化、Go 单元测试、前端类型检查、图标注册校验及 ESLint。 |
| `make clean` | 清理本地构建产物及临时文件。 |

### 2.2 子模块独立调试命令

- **后端独立操作（`cd backend-go/`）**：
  - `make dev`：单独启动后端 Air 热重载（默认监听 3000 端口）；
  - `make test` / `make test-cover`：运行 Go 单元测试 / 统计测试覆盖率；
  - `make fmt`：执行 `gofmt` 格式化；
  - `./build.sh`：一键跨平台交叉编译（输出 Linux/macOS/Windows × amd64/arm64 架构文件）。
- **前端独立操作（`cd frontend/`）**：
  - `npm run dev`：单独启动 Vite 开发服务器（默认端口 5173，内置代理会将 `/api`、`/v1`、`/v1beta` 和 `/health` 自动转发至 3000 端口）；
  - `npm run build`：执行前端生产环境构建，生成 `frontend/dist`；
  - `npm run type-check`：通过 `vue-tsc` 进行严格类型校验；
  - `npm run check:icons`：扫描检查所有使用的 `mdi-*` 图标是否已在配置中按需注册；
  - `npm test`：运行 Vitest 单元测试；
  - `npm run lint` / `npm run lint:fix`：执行 ESLint 代码风格检查与自动修复。

## 3. 本地全量门禁（scripts/check.mjs）

由于本项目未在远程仓库针对分支 Push 或 PR 开启消耗高额 CI 额度的常规检查，**全部代码质量防线均依赖工程师在本地提交前主动执行门禁**。

在根目录执行 `npm run check`（或 `make check`）时，脚本会严格按顺序执行以下检查，任何一项失败即中断：

```
1. ensureHooksPath             -> 校验并设置 Git 钩子目录为 .githooks
2. scripts/eol.mjs --check     -> 校验全仓文件的行尾换行符规则（CRLF / LF）
3. scripts/copy-frontend.mjs   -> 体检前端目标嵌入目录，拦截错误的嵌套目录结构
4. 校验 AGENTS.md 目录登记    -> 核对 AGENTS.md 与实际目录是否一致
5. gofmt -l . (backend-go)     -> 检查 Go 代码格式（只要有任何未格式化文件立即判定失败）
6. go vet & go test (Go)       -> 执行 Go 静态诊断和所有包的单元测试
7. npm run check (frontend)    -> 运行 vue-tsc 类型检查并扫描未注册图标
8. npm test (frontend)         -> 运行前端 Vitest 自动化测试套件
9. eslint (frontend)           -> 执行前端代码规范检查（严格要求 --max-warnings 0）
```

## 4. 前端产物嵌入流水线

网关采用单二进制交付，其前端嵌入流转链路如下：

```
frontend/src/
      │  (执行 npm run build)
      ▼
frontend/dist/
      │  (执行 node scripts/copy-frontend.mjs)
      ▼
backend-go/frontend/dist/
      │  (Go 编译期指令 //go:embed all:frontend/dist)
      ▼
dist/api-proxy-go (最终交付的单个可执行文件)
```

- **统一由脚本处理**：`scripts/copy-frontend.mjs` 会基于脚本自身位置动态计算绝对路径，避免因工程师执行命令所在目录不同而将产物拷贝到错误层级。**请勿手动手动拖拽或手动覆盖 dist 目录**。
- **防嵌套机制**：历史上曾发生过误将目录拷贝成 `backend-go/backend-go/` 导致体积暴增与嵌入失效的事故。拷贝脚本和门禁均内建了防御校验，会自动检测并清理异常嵌套。

## 5. 跨平台发布与版本流转

发布新版本的标准流转步骤：

1. **版本号升级**：使用项目专属的 `version-bump` 技能升级版本号。它会自动同步更新根目录 `VERSION`、前端 `package.json`、锁文件以及 `CHANGELOG.md`；
2. **提交并推送标签**：提交变更后，为当前提交打上形如 `v3.x.x` 的 Git Tag 并推送到远程；
3. **自动化编译构建**：推 Tag 会自动触发 GitHub Actions 的发布流水线（`release-linux.yml`、`release-macos.yml` 与 `release-windows.yml`）。流水线会拉取固定的 Node/Bun/Go 工具链，在 `CGO_ENABLED=0` 静态模式下编译出 6 个主流操作系统与架构的二进制归档（Linux/macOS/Windows 的 amd64 与 arm64）；
4. **整理发布说明**：流水线完成后会自动生成 Draft Release 草稿，随后可通过 `github-release` 技能从 `CHANGELOG.md` 中提取对应版本的中文变更说明并正式发布。

## 6. Docker 容器化部署

### 6.1 多阶段构建设计
仓库提供了官方版 `Dockerfile` 与国内网络加速版 `Dockerfile_China`。两个镜像均采用严谨的三阶段流水线：
- **阶段一（前端构建）**：基于 `node:24-alpine` 镜像，利用 `npm ci` 编译前端静态页面；
- **阶段二（后端编译）**：基于 `golang:1.26-alpine` 镜像，利用 `go mod download` 缓存依赖，执行全栈编译；
- **阶段三（轻量运行时）**：基于极小的 `alpine:3.23` 运行时底座，预装 CA 根证书与时区配置（默认时区设为 `Asia/Shanghai`），仅将上阶段产出的单二进制可执行文件注入运行。

### 6.2 本地镜像构建验证

```bash
# 官方网络环境构建
docker build --target runtime -t api-proxy:local .

# 国内镜像源与代理加速构建
docker build -f Dockerfile_China --target runtime -t api-proxy:local-cn .
```

### 6.3 Docker Compose 生产运行
生产环境推荐使用 `docker-compose.yml` 运行。配置目录与持久化数据映射说明：
- `./.config:/app/.config`：保存配置文件（`config.json`）、运行日志数据库（`logs.db`）以及各类业务 SQLite 库；
- 容器默认分配了稳健的资源约束（限制内存 256MB、CPU 0.5 核），并配置了基于 `/health` 接口的健康探测。

## 7. 日常开发常见踩坑与注意事项

1. **图标未注册导致门禁报错**：
   - 前端为了将打包体积控制在极限大小，禁用了 Vuetify 图标的全量扫描引入。
   - 如果你在 Vue 组件中新写了一个图标（如 `<v-icon :icon="mdiFolderCog" />`），**必须先在 `frontend/src/plugins/vuetify.ts` 的 `iconMap` 中显式登记该图标**，否则在运行 `npm run check:icons` 时会立即中断报错。
2. **路由视图组件必须为“单根 DOM”**：
   - 根组件 `App.vue` 对路由切换启用了淡入淡出过渡动画。
   - 所有放在 `views/*.vue` 下的页面，**最外层必须有且仅有一个真实的 HTML 容器元素**（如 `<div>`）。如果写成多个同级节点，Vue 的动画引擎会丢失挂载参照物，导致路由切换后页面变成完全空白。
3. **ESLint 零警告容忍度**：
   - 项目在本地门禁和构建中执行了 `eslint --max-warnings 0`。
   - 即使是 `no-explicit-any` 或存在未使用的变量这种 Warning 级别的提示，也会直接使门禁挂掉。编写代码时请保持类型严谨，废弃变量加 `_` 前缀或直接清理。
4. **Windows 环境下的软链接陷阱**：
   - Git 在 Windows 环境下默认将软链接解构为包含路径文本的普通文本文件。
   - 因此项目中严禁使用软链接去桥接 `CLAUDE.md` 与 `AGENTS.md`。仓库统一约定 `CLAUDE.md` 仅包含单行 `@AGENTS.md` 引用。
5. **二进制没有 `--version` 标志**：
   - 编译后的二进制可执行文件并未设置类似 `--version` 的独立参数。如果带参数直接启动，依然会作为常规服务运行。如需探查当前运行实例的版本，请访问 `/health` 接口获取 JSON 返回中的详细构建信息。
