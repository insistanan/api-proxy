# 开发说明（development）

本文说明日常开发需要的环境、常用命令、提交前检查，以及构建和发布流程。修改代码前，请同时阅读 [规范与不变量.md](规范与不变量.md)；涉及跨模块改动时，再核对 [架构说明.md](架构说明.md)。

## 环境准备

- Go 版本以 `backend-go/go.mod` 为准，最低 1.26.0，工具链固定 1.26.10；发布 workflow 从该文件读取版本。Go 自动工具链可通过 `go env -w GOTOOLCHAIN=go1.26.10+auto` 更新，不必覆盖基础 Go 安装。
- Node 24.16.0 和 Bun 1.4.4 分别由根 `.node-version`、`.bun-version` 固定，满足 Vite 7 的版本要求。前端依赖可用 `npm ci` 或 `bun install --frozen-lockfile` 安装；发布 workflow 使用固定 Node/Bun，Docker 使用相同 Node 和 npm。仓库保留 `bun.lock` 与 `package-lock.json`，修改依赖后要核对两份锁文件。
- 根 Makefile 需要 make、npm 和 Node。Windows 下未安装 make 时，可以在根目录执行 `npm run check`，完成相同的全量门禁。
- 后端热重载使用 Air v1.67.4，`make lint` 使用 golangci-lint v2.15.0；安装版本在后端 Makefile 中固定，lint 使用 `/v2` 模块路径。仓库没有单独的 .golangci 配置文件。
- 本机开发使用 Git Bash。本文涉及的 Makefile 和 shell 命令均在 Git Bash 中执行。

## 常用命令

| 位置 | 命令 | 说明 |
|---|---|---|
| 根目录 | `make dev` | 同时启动前端 Vite 与后端 Air |
| 根目录 | `make build` | 前端构建 → copy-frontend → Go 构建，产物 `dist/api-proxy-go` |
| 根目录 | `npm run build:desktop` / `make build-desktop` | 当前平台桌面构建，产物 `dist/desktop/` |
| 根目录 | `npm run check:desktop` / `make check-desktop` | 当前宿主平台桌面标签 vet/test，需原生依赖 |
| 根目录 | `make run` | 前端构建并嵌入，然后 `go run` 后端 |
| 根目录 | `make check` / `npm run check` | 全量门禁（见下） |
| 根目录 | `make embed-frontend` / `clean` | 前端构建并复制 / 清理构建产物 |
| `backend-go/` | `make dev` / `build` / `check` / `test` / `fmt` / `lint` | 后端各操作 |
| `backend-go/` | `./build.sh` | 跨平台交叉编译（linux/darwin/windows × amd64/arm64） |
| `frontend/` | `npm run dev` / `build` / `check` / `lint` / `test` | 前端各操作 |

手动编译 Windows amd64 可执行文件时，使用 `dist/api-proxy-windows-amd64.exe`，与 `backend-go/build.sh` 和 `release-windows.yml` 的命名保持一致。根目录 `make build` 仍按 Makefile 的约定输出 `dist/api-proxy-go`。

安装依赖后，在根目录执行 `make dev` 即可同时启动前后端。也可以分别在 `backend-go/` 执行 `make dev`，在 `frontend/` 执行 `npm run dev`；默认端口分别为 3000 和 5173。Vite 会把 `/api`、`/v1`、`/v1beta` 和 `/health` 请求代理到后端，相关环境变量见 `frontend/.env.example`。

## 全量门禁（scripts/check.mjs）

仓库没有分支 push 或 PR 触发的检查 CI，因此提交前需要在本地完成门禁。根目录的 `make check` 与 `npm run check` 等价；前后端子目录中的同名命令只检查各自范围。全量门禁按以下顺序执行：

1. `ensureHooksPath`：确保 `git config core.hooksPath=.githooks`
2. `node scripts/eol.mjs --check`：行尾校验
3. `node scripts/copy-frontend.mjs --check`：检查嵌套 dist 和目标目录类型
4. `gofmt -l .`（backend-go，有输出即失败）
5. `go vet ./...` + `go test ./...`
6. 前端 `npm run check`（type-check + 图标扫描）
7. 前端 `npm test`（Vitest 单元测试）
8. 前端 `npx eslint . --ext .vue,.js,.ts --max-warnings 0`，任何警告都会使检查失败

## 行尾策略（三层保障）

- `.gitattributes` 规定 Windows 工作区使用 CRLF，Go、shell、`.githooks` 和根 `scripts/*.mjs` 使用 LF；`bun.lockb` 按二进制处理。
- `.githooks/pre-commit` 在提交时调用 `scripts/eol.mjs --staged-fix`，修正暂存区中的行尾。
- `scripts/eol.mjs` 提供 `--check` 和 `--staged-fix` 两种模式，分别用于检查行尾和修正暂存区。

这三处共同维护行尾规则，修改时应保持一致。`.gitignore` 中关于 `/skills/` 前导斜杠和嵌套 dist 的注释记录了历史事故原因，调整规则前要先读这些说明。

## 前端产物的构建与嵌入

```
frontend/dist --(scripts/copy-frontend.mjs)--> backend-go/frontend/dist --(go:embed all:frontend/dist)--> 单二进制
```

Makefile、`backend-go/build.sh` 和 release workflow 都通过 `scripts/copy-frontend.mjs` 复制产物。该脚本根据自身位置解析仓库路径，可以避免因执行目录不同而复制到错误位置；复制时会替换目标目录的全部内容，包括旧产物和 `.gitkeep`。前端产物统一由这个脚本处理，不要手工复制。

根目录 `make build` 会先构建前端，再复制产物并编译后端。`backend-go/` 下的 `make build` 和 `build.sh` 只复制已有的 `frontend/dist`，使用前需要先完成前端构建。

历史上曾出现 `backend-go/backend-go/` 和 `frontend/backend-go/` 这类嵌套目录，导致嵌入了错误产物。`.gitignore` 保留了对应的防御规则，门禁也会检查这些目录。脚本的 `--check` 模式只检查目录结构和类型，不验证资源内容是否完整或最新。

## Wails 桌面构建

桌面版固定 Wails v3.1.0，同一个 Go module 通过 `desktop,production` 标签构建。现有 Vue 前端在桌面窗口加载同进程的 `http://127.0.0.1:PORT`，默认端口仍为 3000，保留代理端点和管理 API 鉴权。Windows 用 `-H windowsgui` 去除黑色控制台窗口。端口占用、配置错误、缺少完整前端资源都在窗口显示，不自动换端口。

先在 `backend-go/` 安装 `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0`，并将 Go bin 目录加入 PATH。构建脚本也会从 `go env GOBIN/GOPATH` 查找 CLI，并检查 Go/Wails 版本一致性。

| 平台 | 构建环境 | 运行依赖与产物 |
|---|---|---|
| Windows amd64/arm64 | Windows + Go/Node/Wails，CGO=0；amd64 宿主可构建 arm64 | WebView2 Runtime；`api-proxy-desktop-windows-*.exe` |
| macOS amd64/arm64 | 对应架构 macOS + Xcode Command Line Tools，CGO=1 | macOS 12+ / WKWebView；`api-proxy-desktop-darwin-*.zip`，内含 `.app` |
| Linux amd64/arm64 | 对应架构 Linux + build-essential/pkg-config/libgtk-4-dev/libwebkitgtk-6.0-dev，CGO=1 | GTK4 / WebKitGTK 6.0；`api-proxy-desktop-linux-*.tar.gz` |

在根目录执行以下命令；依赖安装和验证由开发者按需要运行：

```bash
npm run check
npm run check:desktop
npm run build:desktop
# Windows amd64 宿主构建 arm64
npm run build:desktop -- --platform windows/arm64
```

桌面检查是独立入口，默认全量门禁继续检查服务版。`backend-go/desktop/Taskfile.yml` 为同一构建和检查脚本提供 Task 别名。构建先走正式前端 build/copy 链路，再在临时后端源码副本生成资源并打包，不在服务源码目录留下 `.syso`。

桌面版默认采用便携目录：Windows、Linux 和 macOS 裸二进制使用可执行文件所在目录，macOS `.app` 使用应用包的父目录。配置和数据库保存在该目录下 `.config/*`，Windows WebView 缓存保存在 `.config/webview`，不依赖启动时的工作目录。`--data-dir` 可指定现有服务数据的父目录，`--project-dir` 单独指定项目 Skills 的父目录，默认使用数据根目录（其下 `skills/`）。程序所在目录必须可写，写入失败会显式报错，不会自动改用用户配置目录。旧数据不会自动迁移；复用现有目录前先停止原服务，避免两个进程同时管理相同配置与数据库。

桌面版继续按原顺序加载 exe 同目录和工作目录的 `.env`，最后补加载数据根目录 `.env`，不覆盖已设置的环境变量。窗口关闭隐藏到托盘；托盘菜单提供管理窗口、浏览器打开与退出。Linux 托盘依赖 StatusNotifierWatcher，不支持时提示并改为关闭窗口退出。正式退出等待 HTTP 请求排空，再按原顺序清理资源；清理错误显式显示。

当前为未使用开发者证书签名的分发方案；macOS 包执行 ad-hoc 签名，未公证。Linux 包依赖目标系统的动态库，Ubuntu 24.04 构建产物不承诺兼容更旧发行版。Linux 解压后可直接运行二进制；附带 `.desktop` 文件需把程序放入 PATH、将图标安装为 `api-proxy-desktop` 后使用。Windows WebView2 缺失、三平台安装/托盘/外链/退出行为需要实际构建后验收。

## 发布流程

1. 使用 `.claude/skills/` 中的 `version-bump` 技能更新版本并提交，同步 `VERSION`、前端包版本、锁文件中的根包版本和 CHANGELOG。
2. 推送 `v*` tag，触发服务版 `release-linux.yml`、`release-macos.yml`、`release-windows.yml` 以及 `release-desktop.yml`。
3. workflow 从根版本文件配置 Node/Bun，按冻结锁文件安装前端依赖，按 `go.mod` 配置 Go。服务版仍使用 `CGO_ENABLED=0`，构建不执行 `go mod tidy`，以 `-mod=readonly` 阻止修改依赖；ldflags 写入版本、构建时间和提交号。
4. 服务版六个资产和桌面六个资产上传到同一 draft release。桌面 workflow 先执行服务版全量门禁与宿主平台桌面检查，再构建指定平台；Windows arm64 资产由 amd64 宿主交叉构建，运行测试仍为宿主架构。macOS/Linux 使用对应架构 runner。桌面六组构建全部成功后，由独立 job 汇总上传六个资产，避免各架构同时创建发行草稿。手动触发桌面 workflow 可下载 artifact，不创建 Release。所有发布 workflow 在安装工具链前校验 tag 与 VERSION 一致。

workflow、构建脚本和工具链版本文件必须先提交到被 tag 指向的提交，再推送 `v*` tag 才会触发；本地创建 tag 不会运行 GitHub Actions。工作区中尚未提交的桌面构建文件不会包含在旧 tag 的构建中。
5. 最后使用 `github-release` 技能从 CHANGELOG 整理发布公告，更新草稿。

CHANGELOG.md 是中文维护的唯一功能史料，发布前确保其已更新。

## Docker 部署

两个 Dockerfile 都分为三个阶段：先从 Node 24.16.0 镜像准备 Node 和 npm，再在 Go 1.26.10 镜像中执行 `make build`，最后将嵌入前端资源的服务版可执行文件复制到 Alpine 运行镜像。三个阶段统一使用 Alpine 3.23；运行镜像安装证书和时区数据，默认时区为 `Asia/Shanghai`，通过 `/health` 检查服务状态。

前端依赖通过 `npm ci` 按 `package-lock.json` 安装，Go 依赖通过 `go mod download` 下载。依赖安装放在源码复制之前，修改源码或注释时可以复用依赖缓存。构建镜像包含根 `scripts/` 目录，前端产物仍由 `copy-frontend.mjs` 处理。`.dockerignore` 排除本机 `node_modules`、旧构建产物、运行配置和数据库，镜像构建不使用这些本地文件。

`Dockerfile_China` 使用 docker.1ms.run 的基础镜像，将 Alpine 软件源切换到阿里云，并设置国内 Go 代理和 npm registry。两份文件的构建步骤保持一致。

需要验证源码镜像构建时，可在仓库根目录执行：

```bash
docker build --target runtime -t api-proxy:local .
docker build -f Dockerfile_China --target runtime -t api-proxy:local-cn .
```

上述链路已完成源码核对，本轮没有实际构建镜像或启动容器。

`docker-compose.yml` 默认拉取阿里云上的镜像。改用本地构建时，按文件中的注释启用 `build` 配置并移除 `image` 行。`./.config` 挂载用于保存配置和数据库；`./logs` 是旧版挂载，只有将日志路径设为 `/app/logs` 下的文件时才会使用它。启动配置见 README，旧请求与响应日志环境变量只用于迁移缺失的设置字段，之后在设置页维护。compose 的资源上限为 256M 内存和 0.5 CPU。

## 配置生效范围

- 程序依次加载可执行文件所在目录和工作目录中的 `.env`，不会覆盖已有环境变量。`PORT`、`ENV`、`PROXY_ACCESS_KEY`、`ENABLE_WEB_UI`、`LOG_LEVEL` 和 `LOG_TO_CONSOLE` 在启动时读取，修改后需要重启。
- `settings.gateway` 保存请求与响应日志开关、超时、请求体上限、CORS 和指标保留期等策略。旧环境变量只补充缺失字段。日志数据库路径和指标持久化开关重启后生效，其余策略由请求读取运行时快照。
- `settings.disguise` 保存客户端伪装版本和自动跟随开关。保存配置或热重载时会应用本地版本，npm 版本查询在后台执行。
- `config.json` 和数据库默认路径相对于进程工作目录。启动 Release 可执行文件时应固定工作目录，避免在不同目录下创建多套配置。

## 常见坑

- **图标未注册**：前端新用 `mdi-*` 图标必须先在 `src/plugins/vuetify.ts` 的 iconMap 注册（autoImport: false），否则 check:icons 失败
- **视图多根节点**：App.vue 的 `<transition mode="out-in">` 要求视图根节点是单个真实 DOM 元素，否则路由切换整块空白
- **ESLint 零警告**：`--max-warnings 0`，`no-explicit-any` 只是 warn 也会计入，提交前跑 `npm run lint` 确认
- **修改配置文件**：`config.json` 由 fsnotify 热重载（100ms debounce + sha256 比较），改完无需重启；但运行数据都在 `.config/` 下，测试时注意备份
- **Windows 下不要用 symlink 桥接 CLAUDE.md/AGENTS.md**：git 默认 core.symlinks=false，symlink 检出后变成含链接文本的普通文件，静默失效；用 `@AGENTS.md` 一行引用代替
- **EXE 无 `--version` 子命令**：普通参数仍会启动服务；版本可从 `/health` 获取，日志查询入口为 `api-proxy logs`
