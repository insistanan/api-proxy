# 架构说明（architecture）

整体架构、请求流转、调度体系与数据存储。改动跨模块逻辑前必读。规范与不变量见 [规范与不变量.md](规范与不变量.md)。

## 1. 整体形态：单二进制一体化

前端（Vue 3）构建产物经 `go:embed` 嵌入 Go 后端，一个可执行文件同时服务代理客户端与管理界面浏览器。

## 2. 代理请求流转（五协议统一入口）

所有代理端点收敛到 `proxycore.RunProxyRequest`（`handlers/proxycore/protocol.go:77+`），协议差异通过 `ProtocolSpec`（protocol.go:26-61，含 ParseRequest / BuildUpstreamRequest / HandleSuccess / HandleAllFailed 等钩子）注入。

```mermaid
flowchart TD
    REQ["代理端点请求<br/>/v1/* 或 /v1beta/*"] --> AUTH["ProxyAuthMiddleware 认证<br/>（RunProxyRequest 内部调用，非路由层）"]
    AUTH --> BODY["读体 / 解析<br/>ProtocolSpec.ParseRequest"]
    BODY --> MASK["敏感数据脱敏<br/>（sensitive，可逆脱敏热跟随模式）"]
    MASK --> OBS["会话观测 / 请求日志"]
    OBS --> BRANCH{"渠道分支"}
    BRANCH -->|"多渠道"| PICK["ChannelScheduler 选渠<br/>+ ChannelPermit 许可句柄"]
    BRANCH -->|"单渠道"| DIRECT["直连指定渠道"]
    PICK --> BUILD["ProtocolSpec.BuildUpstreamRequest"]
    DIRECT --> BUILD
    BUILD --> SEND["httpclient 发送<br/>（唯一网络出口）"]
    SEND --> UPRESULT{"上游结果"}
    UPRESULT -->|"2xx 但错误信封"| FAIL
    UPRESULT -->|"失败"| CLASS["failover_classify 重试分类<br/>multi_channel_failover / content_policy_retry"]
    UPRESULT -->|"成功"| STREAM{"流式?"}
    STREAM -->|"是"| SSE["HandleStreamResponseCtx<br/>手写 SSE 转发（断连即停）"]
    STREAM -->|"否"| CONV["HandleSuccess<br/>协议转换回客户端口径"]
    SSE --> DONE
    CONV --> DONE["RecordHealth → Release permit"]
    CLASS -->|"可重试"| PICK
    CLASS -->|"全部失败"| FAIL["HandleAllFailed"]
```

要点：

- 新增协议 = 实现 ProtocolSpec 钩子 + 注册端点，不另起炉灶（messages/handler.go:31-86 是典型示例）
- 流式响应必须用 `HandleStreamResponseCtx`（带 context），客户端断连立即停读上游，避免 goroutine 泄漏
- `ChannelPermit`：取得后 defer 释放，结束时 RecordHealth 恰好一次再 Release，均可幂等重复调用
- Messages→Responses 转换时 provider 实例存 gin context 复用，成功阶段必须复用同一实例否则丢 previous_response_id 链

## 3. 调度与稳定性体系

```mermaid
flowchart TD
    SCHED["ChannelScheduler<br/>（每 ChannelKind 一套视图）"] --> METRICS["MetricsManager<br/>按 ChannelKind 分组"]
    SCHED --> SESSION["session<br/>Trace / BaseURL 亲和<br/>（提升 prompt cache 命中）"]
    SCHED --> URLH["urlhealth<br/>多 BaseURL 健康管理与动态排序"]
    SCHED --> CIRCUIT["circuit<br/>三态熔断 Closed / Open / HalfOpen"]
    SCHED --> RATE["ratelimit<br/>滑动窗口限流 + 429 平滑排队"]
    SCHED --> PROFILE["ProfileManager<br/>性能画像（仅观测，不参与选渠）"]
    SCHED --> PERMIT["ChannelPermit<br/>许可句柄（defer 释放）"]
```

- **生产选渠严格按配置顺序**；性能画像仅观测不参与选渠（main.go:209-215，"R6：修正历史误导日志"）
- 渠道状态：active/suspended/disabled（config.go:37），另有 promotion/temporary/deprecated 生命周期（channel_lifecycle worker）
- 五组渠道配置（upstream / responsesUpstream / geminiUpstream / chatUpstream / imagesUpstream）支持 modelMapping 一对多、poolId、vision layer 等调度字段

渠道编排规则（scheduler/selection.go 唯一权威实现）：

- **分组路由**：按分组"匹配词"（请求模型 ID contains，最长匹配优先）命中业务分组；命中分组没有可尝试的渠道（渠道耗尽/停用/熔断中/不支持该模型）时进入兜底分组（default），两种模式都保留
- **位次优先级**：分组内严格按配置位次取第一个可用渠道；RPM、在途负载、延迟、失败率、动态评分一律不参与选渠（失败率仅用于前端展示）
- **渠道内尝试层级**：Key（外层）→ 模型候选（中层）→ 重试次数（内层）；同一个 Key + 同一个模型候选失败 5 次才切换下一个模型候选，模型候选全部失败才换下一个 Key，Key 全部失败才轮到下一个渠道。模型候选按 modelMapping 显式顺序全部遍历，与 Fuzzy 开关无关。重试预算只适用于上游给出了 HTTP 响应的失败（上游错误分类、兼容性重试、2xx 错误信封）；连接失败、响应头超时、响应体读不完整属于"没拿到上游响应"，与模型候选无关，按 Key 级失败处理——标记该 Key 后直接换下一个 Key，不在同一候选上再重试（否则单次请求会在坏渠道上空等 5 × 首字节超时）
- **Fuzzy 关闭**：只尝试命中分组位次第一的渠道，渠道内候选耗尽直接报错阻断，不换渠道（分组兜底仍按规则 1 生效）
- **Fuzzy 打开**：按位次顺序转移；抢优先级（促销期）渠道只在此时生效，支持多个并按其位次整体提前
- **渠道级熔断**：连续失败 5 次 → Open（唯一触发条件），冷却 15 分钟 → HalfOpen 单探测；错误率仅用于展示，不作触发条件；Key 级熔断独立保留
- **图片理解层顺序**：显式配置渠道 → 公用图片理解池 → 同分组图片理解渠道 → 兜底分组图片理解渠道；全部失败直接返回"模型不可用"并阻断，不再切换文本渠道

## 4. 应用装配与生命周期

`newApp()`（main.go:69-380）线性装配：EnvConfig → logger → ConfigManager → 内容安全存储 → sessionManager → metrics → conversationRegistry → URLManager → ChannelScheduler → circuit → CmdGate/内容安全管道 → 可逆脱敏 → piAgent/skills/assistant/eval API → gin 引擎。

- 初始化失败按 `registerCleanup` **逆序清理**（main.go:74-84）
- shutdown 同样逆序：先停数据生产者（scheduler）再关存储；**app struct 字段顺序即构造顺序，两者不可调换**（main.go:37-38、app_lifecycle.go:88-91）

```mermaid
flowchart LR
    INIT["newApp() 线性装配"] --> RUN["运行"]
    RUN --> SHUT["优雅关闭（逆序）<br/>scheduler 先停 → 存储后关"]
```

## 5. 前端架构

```mermaid
flowchart TD
    VIEWS["views/ 13 个路由页面"] --> COMP["components/ 26 个复用组件"]
    VIEWS --> COMPOS["composables/ 12 个<br/>状态与异步流程编排"]
    COMPOS --> STORES["stores/ 6 个 Pinia store<br/>（状态唯一来源 + localStorage 持久化）"]
    STORES --> API["services/api.ts 单例 ApiService<br/>（fetch 封装 + x-api-key）"]
    API -->|"开发：vite 代理→:3000"| BE["Go 后端"]
    API -->|"生产：同域 /api（go:embed）"| BE
    AUTHD["App.vue 全局认证对话框<br/>useAuthFlow（无路由守卫）"] --- VIEWS
```

- 认证是全局对话框模式：未认证时弹密钥 dialog 挡住整个应用，5 次失败锁 5 分钟；仅 401 视为密钥无效
- 五种协议类型（`ApiTab`）贯穿全栈：store 收敛为 `Record<ApiTab, ...>`，`channelApi(type)` 工厂查表返回统一方法集；新增协议要同步改多处
- 错误语义：`ApiError.committed` 表示"配置已原子提交但收尾失败"，此时不自动重试，提示用户刷新
- SSE 因需鉴权用 fetch + readSSEStream 而非 EventSource

## 6. 数据存储

全部 SQLite（modernc.org/sqlite，WAL，`SetMaxOpenConns(1)`），位于运行目录 `.config/`，无 migration 框架（建表靠 `CREATE TABLE IF NOT EXISTS` + config 包内 JSON 迁移）：

| 文件 | 用途 | 使用方 |
|---|---|---|
| `config.json` | 主配置（五组渠道 + settings），热重载，保留 10 份备份 | ConfigManager |
| `logs.db` | 运行日志与请求正文 | logger、cli（`api-proxy logs`） |
| `blocked-logs.db` | 拦截记录 + 危险命令闸门 | sensitive、llmgate |
| `conversations.db` | 对话注册表 + Responses 会话 | conversation、session |
| `metrics.db` | 指标持久化（可选） | metrics |
| `redaction-mappings.db` + `master-key` | 可逆脱敏持久映射（AES-256-GCM） | sensitive（Veil ADR 0004） |
| `assistant.db` | AI 配置助手 | assistant |
| `eval.db` | 评测工作台题库与批次 | eval |

## 7. 鉴权模型（三层）

| 层 | 中间件 | 保护对象 | 密钥来源 |
|---|---|---|---|
| 页面开关 | WebAuthMiddleware | WebUI 页面（ENABLE_WEB_UI） | 只管页面开关，不碰管理业务 |
| 管理 API | AdminAuthMiddleware（**必须显式绑定在路由组上**，漏绑会打 `[Auth-Warn]`） | `/api/*` | PROXY_ACCESS_KEY |
| 代理端点 | ProxyAuthMiddleware（RunProxyRequest 内部调用） | `/v1/*`、`/v1beta/*` | x-api-key / Authorization Bearer / x-goog-api-key 三种提取方式 |

`/health` 固定公开（与 Dockerfile HEALTHCHECK 一致）。v3.3.0 修复过 WebAuthMiddleware 扩展名绕过（7e0b11b），改动鉴权相关代码时格外谨慎。
