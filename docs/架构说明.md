# 架构说明（architecture）

本文说明前后端如何协作、代理请求如何流转，以及调度、资源管理和数据存储的职责划分。修改跨模块逻辑前，应先核对这里描述的流程，再阅读 [规范与不变量.md](规范与不变量.md) 中的行为约束。

## 1. 整体形态：单二进制一体化

Vue 3 前端构建后，通过 `go:embed` 嵌入 Go 后端。部署时，一个可执行文件就在同一端口提供代理 API、管理 API 和 Web 管理界面。

构建入口通过标签选择：默认 `!desktop` 是现有服务版，`desktop,production` 是 Wails v3.1.0 桌面版。桌面窗口加载同进程 Gin 的 `http://127.0.0.1:PORT`，外部 CLI 和浏览器继续访问这个端口；认证、协议、fetch/SSE 和前端资源共用。外链经过桌面消息处理交给系统浏览器，协议限制为 http、https 和 ccswitch。Windows/macOS 使用原生来源信息校验，Linux Wails 不提供消息 frame 身份，当前管理页不加载不可信 iframe。

```mermaid
flowchart LR
```

`ChannelKind` 和 `ServiceType` 描述的是请求的不同侧面。`ChannelKind` 区分 messages、responses、gemini、chat 和 images 五类入口，也是指标分组的依据；`ServiceType` 则表示 openai、claude、gemini 或 responses 上游服务类型。共享准入按实际上游协议分配名额：Images 的原生 openai 上游会识别为 `images`，因此不会与 Chat 混用名额。相关定义见 `scheduler/channel_scheduler.go` 和 `config/config_concurrency.go`。

## 2. 代理请求流转（五协议统一入口）

五类协议的主请求由 `handlers/proxycore/protocol.go` 中的 `RunProxyRequest` 统一编排，各协议通过 `ProtocolSpec` 提供解析、请求构造和响应处理等差异逻辑。下图描述这条主流程。

Responses `/compact` 使用独立的控制请求入口，仍复用选渠、上游尝试、内容安全检查和会话归属机制，但不会发起图片理解调用。Messages `count_tokens` 和模型目录也有各自的处理入口。

```mermaid
flowchart TD
    REQ["代理端点请求<br/>/v1/* 或 /v1beta/*"] --> AUTH["ProxyAuthMiddleware 认证<br/>（RunProxyRequest 内部调用，非路由层）"]
    AUTH --> BODY["读体 / 解析<br/>ProtocolSpec.ParseRequest"]
    BODY --> MASK["敏感数据脱敏<br/>（sensitive，可逆脱敏热跟随模式）"]
    MASK --> OBS["会话观测 / 请求日志"]
    OBS --> BRANCH{"渠道分支"}
    BRANCH -->|"多渠道"| PICK["ChannelScheduler 选渠<br/>+ ChannelPermit 许可句柄"]
    BRANCH -->|"单渠道 / 指定渠道"| DIRECT["固定渠道内轮转 URL / Key"]
    PICK --> BUILD["ProtocolSpec.BuildUpstreamRequest"]
    DIRECT --> BUILD
    BUILD --> ADMIT["upstreamcontrol 共享准入<br/>并发 / FIFO / 冷却 / 请求预算"]
    ADMIT --> SEND["httpclient 发送"]
    SEND --> UPRESULT{"上游结果"}
    UPRESULT -->|"2xx 但错误信封"| CLASS
    UPRESULT -->|"失败"| CLASS["failover_classify 重试分类<br/>multi_channel_failover / content_policy_retry"]
    UPRESULT -->|"成功"| STREAM{"流式?"}
    STREAM -->|"是"| SSE["HandleStreamResponseCtx<br/>手写 SSE 转发（断连即停）"]
    STREAM -->|"否"| CONV["HandleSuccess<br/>转换为客户端协议"]
    SSE --> DONE
    CONV --> DONE["记录结果 / 关闭上游 body<br/>归还执行名额与选渠许可"]
    CLASS -->|"可重试"| BRANCH
    CLASS -->|"全部失败"| FAIL["HandleAllFailed"]
```

要点：

- 新增协议时，需要实现 `ProtocolSpec` 钩子、注册端点，并接入对应的配置、指标和管理路由。现有实现可参考 `handlers/messages/handler.go`。
- Provider 的流式转换使用 `HandleStreamResponseCtx`。原生转发也需要传播请求 context，并在退出时关闭上游 body，保证客户端断连后停止读取。
- 取得 `ChannelPermit` 后用 defer 登记释放，结束时先记录一次健康结果，再释放许可。相关方法支持幂等调用，但一个尝试只能记入一个健康结果。
- Messages 转换为 Responses 时，构造请求与处理成功响应必须复用同一个 Provider 实例。实例保存在 Gin context 中，重新创建会丢失 `previous_response_id` 链。
- Claude 原生上游（`serviceType=claude`）的非流式响应在无需校正 usage 时原样下发，保留 `safeguards`、`safeguard_results` 等未知字段，也不改写 tool-use ID。需要校正 usage 时，只修改对应字段。其他上游仍需协议转换，不能承担 Claude Code 服务端分类器。

## 3. 调度与稳定性体系

```mermaid
flowchart TD
    SCHED["ChannelScheduler<br/>（每 ChannelKind 一套视图）"] --> METRICS["MetricsManager<br/>按 ChannelKind 分组"]
    SCHED --> SESSION["session<br/>Trace / BaseURL 亲和<br/>（提升 prompt cache 命中）"]
    SCHED --> URLH["urlhealth<br/>多 BaseURL 健康管理与动态排序"]
    SCHED --> CIRCUIT["circuit<br/>三态熔断 Closed / Open / HalfOpen"]
    SCHED --> PROFILE["ProfileManager<br/>性能画像（仅观测，不参与选渠）"]
    REPORT["管理性能报告<br/>/api/performance/report"] --> PROFILE
    SCHED --> PERMIT["ChannelPermit<br/>许可句柄（defer 释放）"]
    SEND["httpclient 发送出口"] --> ADMIT["upstreamcontrol<br/>共享并发 / FIFO / 429 冷却 / 请求预算"]
    CONFIG["ConfigManager 配置发布"] -->|"更新准入规则"| ADMIT
```

生产请求默认按配置顺序选择渠道。开启促销的健康渠道可以在所属分组内临时优先，但仍需通过健康检查和熔断准入；对话路由覆盖的优先级高于促销，促销也不会跨越分组。时长或成功请求次数中的任一限制达到后，渠道恢复原有顺序。恢复探测同样按配置顺序执行，性能画像只用于观测，不参与排序。

失败率用于跳过不健康渠道，不用于重新排序。只有开启 Fuzzy 的多渠道请求允许故障后切换渠道，单渠道请求仍需遵守共享准入限制。熔断器同时检查连续失败次数和错误率，默认阈值为连续失败 4 次或错误率达到 60%，冷却时间为 60 秒。

`upstreamcontrol` 按 URL、实际上游协议和 API Key 汇总准入规则。相同组合即使出现在不同入口，也共用最小的配置并发上限。配置提交或热重载时，`ConfigManager.publishConfigLocked` 更新规则，同时保留正在执行的请求计数和 FIFO 队列。每个组合默认允许 5 个并发请求、3 个排队请求，单次排队最多等待 10 秒。取消请求会退出队列，失败重试需要重新排队，上游响应 body 关闭后归还执行名额。主请求、辅助推理和兼容重试共用最多 12 次发送、累计 30 秒准入等待的预算。

渠道状态包括 active、suspended、disabled、deprecated 和 deleted。临时渠道到期后转为 deprecated，弃用超过 3 天后转为 deleted，保留删除占位；促销则按时长或请求次数结束。生命周期处理见 `config/config_utils.go`、`config/config_lifecycle.go` 和 `config/config_channel_status.go`。

五组渠道配置分别保存在 upstream、responsesUpstream、geminiUpstream、chatUpstream 和 imagesUpstream 中，支持 `modelMapping` 一对多、`poolId` 和 vision layer 等字段。五类管理路由由 `setupChannelAdminAPI` 统一装配，复用同一组 CRUD handler；性能报告由管理 handler 直接读取 `ProfileManager` 快照。

## 4. 应用装配与生命周期

`newApp()` 按依赖顺序创建组件：先读取启动配置并初始化 ConfigManager，迁移缺失的旧环境变量设置；确定日志路径和指标保留期后，再创建日志、内容安全、会话、对话注册表和指标存储。随后装配 URL 管理、调度器、熔断器、命令闸门和可逆脱敏，最后注册 pi-agent、skills、assistant 等管理接口，并创建 Gin 引擎。

- 每个资源创建成功后登记释放动作。启动失败和正常关闭都通过 `app.shutdown()` 按逆序清理，重复或并发关闭只释放一次。一项清理失败时，仍继续回收其他资源，并汇总错误。
- 正常关闭先等待在途 HTTP 请求完成。若等待超时，则关闭连接以触发请求取消，待 handler 退出后再释放应用资源。后台任务的 `Stop` 也要等循环实际退出，之后才能关闭依赖的存储；日志存储最后关闭。
- 桌面版 worker 独占网关生命周期。第一次退出请求先取消 worker，并保持界面线程运行；worker 完成 HTTP 排空和资源清理后再正式退出。worker 的窗口更新异步投递，避免退出时双方相互等待。关闭窗口通常隐藏到托盘，托盘不可用时关闭窗口退出；相同数据目录通过 Wails 单实例锁避免重复启动桌面实例，服务版不共用该锁。
- 调度器构造成功前，装配层负责回收指标和 Trace 亲和相关资源；构造成功后，由调度器统一停止这些组件。已启用的指标存储若初始化失败，启动直接返回错误。
- 请求与日志策略保存在 `settings.gateway`，旧环境变量只用于迁移缺失字段。客户端伪装版本保存在 `settings.disguise`，启动、保存设置和文件热重载时立即应用本地版本。后台 npm 查询只更新 latest 缓存，保存接口不等待网络；关闭自动跟随后，不使用 latest。状态接口返回查询错误和最后成功时间，应用关闭时会取消查询并等待任务退出。

```mermaid
flowchart LR
    INIT["newApp() 线性装配"] --> RUN["运行"]
    RUN --> DRAIN["停止接收并排空 HTTP 请求"]
    DRAIN --> SHUT["逆序清理<br/>后台生产者退出 → 关闭依赖存储"]
```

## 5. 前端架构

```mermaid
flowchart TD
    VIEWS["views/ 路由页面"] --> COMP["components/ 复用组件<br/>channel/ 表单与弹窗 · settings/ 设置分区"]
    VIEWS --> COMPOS["composables/<br/>编辑草稿与异步流程编排"]
    COMPOS --> STORES["stores/ Pinia store<br/>（共享领域状态唯一来源 + 持久化）"]
    COMPOS --> API
    STORES --> API["services/api.ts 兼容门面<br/>领域服务 → http.ts（fetch + x-api-key）"]
    API -->|"开发：vite 代理→:3000"| BE["Go 后端"]
    API -->|"生产：同域 /api（go:embed）"| BE
    AUTHD["App.vue 全局认证对话框<br/>useAuthFlow（无路由守卫）"] --- VIEWS
```

- 认证由全局密钥对话框处理，未认证时阻止用户操作应用。连续 5 次认证失败会锁定 5 分钟，只有 401 响应会被视为密钥无效。
- `ApiTab` 表示五种入口协议。store 使用 `Record<ApiTab, ...>` 分组保存数据，`channelApi(type)` 返回对应协议的共用操作方法。新增协议时，需要同步修改类型、store、API 工厂和路由校验。
- `ApiError.committed` 表示配置已经原子提交，但后续处理失败。此时不能自动重试，界面应提示用户刷新并查看实际状态。
- 设置分区和渠道弹窗共用父级编辑器，切换分区时保留局部草稿。已保存的共享渠道数据由 store 持有，取消编辑不会修改这些数据。
- 各领域 API 服务声明端点和返回类型，`http.ts` 统一处理鉴权、响应解析和错误，`api.ts` 保留原有导入入口和方法名。需要鉴权的 SSE 通过 fetch 和 `readSSEStream` 读取，以便携带访问密钥。

## 6. 数据存储

主配置保存在 JSON 文件中，业务数据使用 modernc.org/sqlite，并开启 WAL。日志库将写入与查询分开，使用一个写连接和最多 4 个只读连接；其余业务库使用单连接。各存储自行执行建表和列升级 SQL，JSON 配置迁移由 config 包处理，没有外部 migration 框架。

服务版默认文件路径相对于进程工作目录；桌面版相对于可执行文件所在目录（macOS `.app` 使用应用包的父目录）或 `--data-dir`。两者保留相同文件结构，没有自动移动旧数据；Windows 桌面 WebView 缓存保存在 `.config/webview`。自定义绝对日志路径原样使用，相对日志路径按对应运行根目录解析，不回写配置。项目 Skills 独立使用 `--project-dir`，默认使用桌面数据根目录下的 `skills/`。各文件的用途如下：

| 文件 | 用途 | 使用方 |
|---|---|---|
| `.config/config.json` | 主配置（五组渠道 + settings），热重载，保留 10 份备份 | ConfigManager |
| `.config/logs.db` | 运行日志、流量正文、正文去重引用与会话摘要索引 | logger、metrics.RequestLogStore、cli（`api-proxy logs`） |
| `.config/blocked-logs.db` | 拦截记录 + 危险命令闸门 | sensitive、handlers/hooks |
| `.config/conversations.db` | 对话注册表 + Responses 会话与 response ID 归属 | conversation、session |
| `.config/metrics.db` | 指标持久化（可选） | metrics |
| `.config/redaction-mappings.db` + `.config/master-key` | 可逆脱敏持久映射（AES-256-GCM） | sensitive（Veil ADR 0004） |
| `.config/assistant.db` | AI 配置助手 | assistant |

## 7. 鉴权模型（三层）

| 层 | 中间件 | 保护对象 | 密钥来源 |
|---|---|---|---|
| 页面开关 | WebAuthMiddleware | WebUI 页面（ENABLE_WEB_UI） | 只管页面开关，不碰管理业务 |
| 管理 API | AdminAuthMiddleware（**必须显式绑定在路由组上**，漏绑会打 `[Auth-Warn]`） | `/api/*`、`/admin/*` | PROXY_ACCESS_KEY，经 x-api-key / Authorization Bearer / x-goog-api-key 提取 |
| 代理端点 | ProxyAuthMiddleware（主流程或独立控制入口内部调用） | `/v1/*`、`/v1beta/*` | 同一个 PROXY_ACCESS_KEY，支持上述三种提取方式 |

`/health` 固定公开（与 Dockerfile HEALTHCHECK 一致）。v3.3.0 修复过 WebAuthMiddleware 扩展名绕过（7e0b11b），改动鉴权相关代码时格外谨慎。
