# 历史演进与重大设计决策（History）

本文档梳理了 **api-proxy** 的发展历程、重大技术重构以及关键架构决策背后的思考，帮助开发者理解系统现状形成的深层原因。版本详细变更见根目录的 [CHANGELOG.md](../CHANGELOG.md)。

## 2. 关键架构决策与背景

### 2.1 为什么将代理主流程收敛到统一编排引擎（RunProxyRequest）？
在早期版本中，各个协议端点（如 `/v1/messages` 与 `/v1/chat/completions`）各自实现了一套选渠、重试、错误处理和日志记录逻辑。这导致新增功能（如添加安全过滤或修改熔断策略）时，需要在每个端点重复编写代码，极易产生行为不一致。
- **现行设计**：将鉴权、请求解析、脱敏、选渠、准入排队、发送、流式/非流式响应转换抽象为标准流水线。具体协议仅需实现 `ProtocolSpec` 接口来处理自身特有的请求组装和响应解析逻辑，极大提升了代码的可维护性。

### 2.2 为什么共享准入控制必须按“实际凭据”聚合？
在多渠道运营中，管理员常常配置多个逻辑渠道（例如“主通道”、“备用低延迟通道”），但它们底层填写的 API Key 和目标服务地址是完全一致的。
- **历史问题**：最初并发限制是针对每个渠道独立配置的。当流量激增时，两个渠道同时发起并发请求，瞬间导致上游因超出物理 Key 的 RPM/TPM 配额而抛出 429。
- **现行设计**：系统在内部自动提取 `[目标 URL + 实际上游协议 + API Key]` 作为统一标识。不论请求来自哪个逻辑渠道，凡是命中相同物理凭据的流量，全部纳入统一的并发计数器与 FIFO 排队队列，彻底杜绝了上游配额击穿。

### 2.3 为什么放弃渠道定价与计费统计模块？
在 v3.2 之前，系统曾包含渠道定价与调用计费功能。
- **废弃原因**：不同上游渠道的计费模式极度复杂且瞬息万变（存在阶梯计费、Prompt Cache 命中折扣、汇率波动及非官方渠道自定义折率等），代理网关无法获取完全可信的真实扣费凭证。维护这类复杂规则的成本远超其实际收益，且经常给用户造成数字误导。
- **现行设计**：网关只专注统计最客观、不可争议的指标——物理 Token 消耗量、请求次数、首字延迟（TTFT）与传输速率（TPS），将财务账单核算剥离出网关核心。

### 2.4 为什么可逆脱敏必须支持“流式实时还原”？
许多大模型在接收到含有敏感信息（如云厂商 AccessKey、私人密码）的提示词时会触发安全风控，或者用户不希望机密外泄至第三方大模型。
- **痛点**：如果仅做单向替换，大模型返回的结果中引用的变量名也会变成掩码，导致客户端代码无法直接使用。
- **现行设计**：网关在请求发送前将敏感字符替换为占位掩码，并将原始映射存入本地加密数据库。当模型以 SSE 流式下发响应时，网关利用自研的状态机在数据流中实时匹配掩码并还原为原始值，使客户端和本地代码完全感知不到脱敏过程的存在。

## 3. 历史事故防范（已固化为工程规章）

在项目迭代过程中踩过的一些典型坑，目前均已沉淀为固化的自动化门禁与防御规则：

1. **嵌套产物目录导致构建污染**：历史上曾因构建脚本相对路径处理不当，生成了类似 `backend-go/backend-go/` 的错误嵌套目录并打入包中。现已在 `.gitignore` 中加入针对性防护，并在 `scripts/copy-frontend.mjs --check` 门禁中加入嵌套目录阻断检查。
2. **根目录忽略规则误伤后端源码**：曾因在 `.gitignore` 中配置了泛化的 `skills/`，导致后端 `internal/admin/skills` 包被 Git 误忽略。现已明确限定忽略规则的作用域（如必须使用 `/skills/` 前导斜杠声明根路径）。
3. **性能画像误导选渠**：早期的日志输出容易让人误以为 TPS 评分高低会决定路由。现已明确画像仅用于监控看板，绝不作为选渠因子，并在规范中永久固定了“严格配置先后顺序 + 熔断过滤”的选渠确定性原则。
